# 0009 — A `sending` status and reconciliation sweep to close the crash-window bug

## Context
The recovery worker (`backend/src/workers/recoveryWorker.ts`) claims a cart by atomically writing `pending -> sent` *before* calling Twilio — intentional, since it's what stops a retried/duplicate BullMQ job from double-sending. But if the process crashed between that claim and the Twilio call resolving, the cart was left permanently `sent` with no message ever delivered, and nothing ever revisited it: the worker's own short-circuit (`if status !== 'pending', skip`) meant a redelivered job for that cart silently no-op'd forever. This was logged in `state.md` as accepted technical debt, then the user asked for it to actually be fixed.

## Decision
1. Add a `sending` status between `pending` and `sent`/`failed`. The claim now writes `pending -> sending` (same double-send-prevention reasoning, just landing on an intermediate state); a confirmed successful send writes `sending -> sent` (this is also the *only* place `sent_at` is set now — previously it was set at claim time, which was itself a smaller timestamp-semantics bug: `sent_at` should mean "confirmed delivered," not "attempted"); a failed send writes `sending -> failed`.
2. Add a dedicated `sending_at` column, set only by the claim transition, so a reconciliation sweep can measure staleness without depending on `updated_at` (which unrelated writes could otherwise reset, making the sweep's timing unreliable).
3. A reconciliation sweep (`cartService.reapStaleSending`, `db.reapStaleSendingCartsAsFailed`) bulk-transitions any cart that's been `sending` for longer than `RECOVERY_SENDING_TIMEOUT_MINUTES` (default 5) to `failed`. It runs once at worker-process startup (the realistic crash-then-restart recovery path) and on a 60s interval while the process stays up (a backstop for a hang that doesn't crash the process).
4. Two complementary mitigations reduce how often the sweep is actually needed: an explicit 20s timeout on the Twilio client (the more direct fix for "call hangs without a crash"), and a 60s `lockDuration` on the BullMQ `Worker` (comfortably above that timeout) so BullMQ doesn't mistake a legitimately-in-flight send for a stalled job and redeliver it concurrently.

## Alternatives considered
- **Full outbox pattern / two-phase commit against Twilio** — would give true exactly-once delivery guarantees, but is real distributed-transaction machinery for a 2-day MVP with a WhatsApp *Sandbox* (not even a production channel). Rejected as disproportionate to the actual stakes here.
- **Resetting a stale `sending` cart back to `pending`** (so the worker retries the send) instead of `failed` — rejected: if the "stalled" send actually succeeds later, resetting to `pending` risks a genuine double-send once the job is retried. `failed` is the safe terminal choice; it requires manual follow-up but can never cause a duplicate message.
- **Relying only on the periodic sweep, no Twilio timeout** — rejected per review feedback: an unbounded Twilio call is the more direct bug to fix, and doing so makes the sweep pure defense-in-depth rather than the primary hang-recovery mechanism.

## Consequences
- Migration `0004_add_sending_status.sql` must be applied and committed before worker code that writes `'sending'` runs, or those writes fail the old CHECK constraint. In this single-environment local-dev setup: run `npm run migrate` before (re)starting `npm run worker`.
- **Residual accepted trade-off**: if a Twilio call is legitimately still in-flight when the sweep's threshold elapses (extremely unlikely given the 20s client timeout and 5-minute default threshold, but not impossible), the sweep can mark the cart `failed` out from under a call that then goes on to succeed. The worker's own `sending -> sent` transition would then no-op (the row's no longer `sending`) — this is logged as a warning with the Twilio SID so it's auditable rather than silently invisible, but the cart itself stays `failed` and needs a human to notice and correct it. This is intentionally accepted as a far safer failure mode than the bug being fixed here ("false sent, invisible forever").
- `failed` remains a terminal status in this MVP — nothing automatically retries a `failed` cart. A stale-`sending`-turned-`failed` cart and a "Twilio genuinely rejected this" `failed` cart are indistinguishable by status alone; only the log line (for the reap case) or the original error message (for a genuine Twilio rejection) tells them apart.
