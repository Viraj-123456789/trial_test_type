- Documentation scaffolding created: `structure.md`, `flow.md`, `adr/`, `CLAUDE.md`.
- **Postgres schema + migrations** (`backend/src/db/migrations/`): `sellers`, `abandoned_carts`, mock `orders`. Custom TS runner (`backend/src/db/migrate.ts`) tracks applied files in `schema_migrations`. Verified against the docker-compose Postgres — migrations apply cleanly and re-running is a no-op.
- **Mock storefront** (`mock-storefront/`): standalone Express app on `MOCK_STOREFRONT_PORT` (4000). `POST /simulate/checkout` and `POST /simulate/order` build Shopify-shaped `checkouts/create`/`orders/create` payloads (fixed fixture pool of customers/products, all fields overridable) and fire them at `BACKEND_WEBHOOK_URL` with real Shopify-style headers (`X-Shopify-Topic`, `X-Shopify-Shop-Domain`, `X-Shopify-Hmac-Sha256` computed the same way Shopify computes it — base64 HMAC-SHA256 of the raw body against `MOCK_STOREFRONT_WEBHOOK_SECRET`).
- **`POST /webhooks/checkout`** (`backend/src/routes/webhooks.ts`): verifies `X-Shopify-Hmac-Sha256` against the raw request body (see ADR-0007 — must use `req.rawBody`, not re-stringified JSON), looks up the seller by `X-Shopify-Shop-Domain`, validates the payload shape, then `cartService.recordAbandonedCart()` inserts into `abandoned_carts` (`ON CONFLICT (seller_id, checkout_id) DO NOTHING` — duplicate Shopify webhook deliveries are a no-op, no double-enqueue) and `workers/recoveryQueue.ts` enqueues a BullMQ delayed job (producer side only; the processor is step #4). Also added: `backend/src/config/env.ts` (centralized env loading), `models/seller.ts` + `models/abandonedCart.ts` (row↔domain mapping, including a fix for pg returning BIGINT as strings — see comment in `db/pool.ts`), `db/sellers.ts` + `db/abandonedCarts.ts` (query layer), `services/shopifyWebhookAuth.ts` (HMAC verification), `app.ts`/`server.ts`, and `db/seed.ts` (inserts the one demo seller matching `MOCK_SHOP_DOMAIN`).
- Verified end-to-end live (Postgres + Redis + both apps running): happy path (200, row inserted, BullMQ job visible in Redis), bad signature (401), unknown seller (404), duplicate delivery (200 with `duplicate:true`, no second job).
- **Recovery worker** (`backend/src/workers/recoveryWorker.ts`, run as its own process via `npm run worker` / `backend/src/worker.ts` — separate from the Express server per ADR-0001): consumes `RECOVERY_QUEUE_NAME` jobs. Looks up the cart, short-circuits if it's no longer `pending`, calls `orderService.checkIfOrdered()` (scoped by `sellerId` + `checkoutId` — a correction to flow.md's single-arg sketch, since checkout ids are only unique per seller). If an order exists → `cartService.markRecovered()`. If not → **atomically claims the cart first** (`markCartSentIfPending`, pending→sent, *before* calling WhatsApp) and only then calls `whatsappService.sendRecoveryMessage()` — currently a **stub** that logs the would-be message instead of calling Twilio (real integration is step #5). Added `db/orders.ts` + `models/order.ts`, `findSellerById` in `db/sellers.ts`, `markCartRecoveredIfPending`/`markCartSentIfPending`/`findCartById` in `db/abandonedCarts.ts`, `services/orderService.ts`, `services/whatsappService.ts` (stub), and `markRecovered`/`markSent` in `services/cartService.ts`.
- Verified live: seeded a `pending` cart with no matching order → worker claimed it, transitioned to `sent`, logged the stub WhatsApp message. Seeded a second cart, manually inserted a matching `orders` row (simulating what step #6's route will do) → worker marked it `recovered`, no message sent. Manually re-enqueued a duplicate job for the already-`sent` cart → worker logged "already sent, skipping" and `sent_at` was unchanged — confirms the double-send fix actually works, not just that the code compiles.
- **Real Twilio WhatsApp send** (`services/whatsappService.ts`): stub replaced with the `twilio` SDK. Twilio client is constructed lazily (not at module load) so the rest of the app keeps working before a Twilio Sandbox account exists — only an actual send attempt requires real credentials (`config/env.ts`'s `twilioAccountSid`/`twilioAuthToken`/`twilioWhatsappFrom` are intentionally optional, not `required()`). On failure (missing creds, non-E.164 phone, Twilio API error) `sendRecoveryMessage()` returns `{ok: false, error}` rather than throwing; the worker then calls the new `cartService.markFailed()` (`db.markCartFailedIfSent`: atomic `sent → failed`, correcting the optimistic claim from `markSent()`) so a send failure is reflected in the DB instead of silently leaving the cart mislabeled `sent`.
- Verified live with the real (blank) `.env` Twilio credentials — i.e. the actual state anyone will be in before setting up a sandbox account: worker started fine (no crash from missing creds), a real webhook → delayed job → send attempt correctly failed with a clear "TWILIO_ACCOUNT_SID/TWILIO_AUTH_TOKEN are not set" message and the cart landed in `failed`. Also verified the E.164 phone-format guard the same way (non-`+`-prefixed phone → `failed` with a clear error). Have not verified an actual successful Twilio delivery — no real Sandbox account/credentials available in this environment; that step is on whoever sets up Twilio next.
- **`POST /webhooks/order`** (`backend/src/routes/webhooks.ts`): same signature-verification/seller-lookup/payload-validation shape as the checkout route. `orderService.recordOrder()` inserts into `orders` (`ON CONFLICT (seller_id, checkout_id) DO NOTHING` — duplicate delivery, same idempotency pattern as the checkout side), then always calls `cartService.matchOrderToCart()` (even on a duplicate — its own `WHERE status = 'sent'` guard makes re-running it a safe no-op). `matchOrderToCart` only transitions a `sent` cart to `recovered`, looked up by `(seller_id, checkout_id)` since the order webhook only knows the checkout id, not our internal cart id — deliberately does **not** touch a `pending` cart, since that's the worker's own job (an order that arrives before the delay elapses is caught there instead, not here), so the two paths can't race over the same status column. Added `db.insertOrderIfNew`, `db.markCartRecoveredIfSent`, `services/orderService.recordOrder`, `cartService.matchOrderToCart`.
- Verified live: checkout → (manually set to `sent`, since no real Twilio account exists here to produce a genuine successful send) → matching order webhook → cart correctly transitioned `sent → recovered`, order row recorded. Also verified: order for a checkout with no cart at all (`recovered:false`), duplicate order delivery (`duplicate:true`, `recovered:false` since the cart's no longer `sent`), bad signature (401), unknown seller (404).
- **Bug-fix pass** on three items from "known technical debt":
  - **Crash-window fix** (ADR-0009): added an intermediate `sending` status (migration `0004_add_sending_status.sql`) so "claimed, attempting to send" is distinguishable from "confirmed sent." The claim is now `pending -> sending`, a confirmed send is `sending -> sent` (this is also now the only place `sent_at` gets set — previously it was set at claim time, a smaller timestamp-semantics bug), and a failure is `sending -> failed`. A reconciliation sweep (`cartService.reapStaleSending`, run at worker startup and every 60s via `backend/src/worker.ts`) bulk-corrects any cart stuck `sending` past `RECOVERY_SENDING_TIMEOUT_MINUTES` (default 5) to `failed`, using a dedicated `sending_at` column rather than the overloadable `updated_at`. Added an explicit 20s Twilio client timeout (`whatsappService.ts`) and a 60s BullMQ `lockDuration` (`recoveryWorker.ts`) as complementary mitigations that shrink how often the sweep is actually needed. Renamed `markCartSentIfPending`→`markCartSendingIfPending`, `markCartFailedIfSent`→`markCartFailedIfSending`; added `markCartSentIfSending`, `reapStaleSendingCartsAsFailed`.
  - **Down-migration support** (ADR-0008, amends ADR-0006): every migration now has a paired `.down.sql`; `npm run migrate:down [steps]` rolls back the N most-recently-applied migrations in reverse order. This was an explicit reversal of ADR-0006's "no down-migrations" consequence, done at the user's request — the rest of that ADR (raw SQL + custom runner over a framework) stands unchanged.
  - **`qs` advisory fixed**: found that `qs@6.16.0` actually patches it, but `express`/`body-parser`'s `~6.15.1` semver range blocked a plain install from reaching it — added `"overrides": {"qs": "^6.16.0"}` to both `backend/package.json` and `mock-storefront/package.json`. `npm audit` now reports 0 vulnerabilities in both.
  - Verified live: manually inserted a `sending` cart with a backdated `sending_at` → startup sweep reaped it to `failed`; inserted another mid-run → the periodic 60s sweep caught it too (not just startup). Re-ran the normal pending→sending→failed path (no real Twilio creds here) and the pending→recovered (already-converted) path — both still correct through the renamed functions. Full `migrate`/`migrate:down`/`migrate` cycle (including a 2-step rollback) verified against the live Postgres.
  - Left deferred, unchanged, at the user's explicit choice: checkout-id JSON-number precision loss (still only matters once real Shopify integration exists, which stays cut from this MVP).

## What's deliberately not built (and why)
- **Multi-store OAuth onboarding** — cut from MVP, doesn't change the core story (webhook → delay → send → confirm).
- **A/B testing of message copy** — cut from MVP, adds complexity with no demo value.
- **SMS/email fallback channels** — cut from MVP, the whole pitch rests on WhatsApp's open-rate advantage.
- **Per-product discount logic** — cut from MVP; one static discount code per seller is enough to tell the story.
- **Real Shopify integration** — deferred, not rejected. Mock storefront fires Shopify-shaped payloads so this is a config swap later, not a rewrite (see ADR-0005).

## Known technical debt
- Twilio sandbox's join-code / 24h-window / template constraints (see ADR-0004) — real WhatsApp send is now wired up, but not yet verified against an actual Sandbox account (no credentials available in this environment). Whoever sets up Twilio next should join the sandbox with the demo recipient number and confirm a real message arrives.
- ~~Idempotency in the worker's "check then send" step~~ ✅ resolved — atomic `pending -> sending` claim, verified live against a manually duplicated job.
- ~~Crash between claiming a cart and running the failure-correction~~ ✅ resolved (ADR-0009) — a `sending` intermediate status + reconciliation sweep (startup + every 60s) now catches a cart orphaned mid-send and marks it `failed` within `RECOVERY_SENDING_TIMEOUT_MINUTES`, verified live. **Residual accepted trade-off**: a Twilio call that's legitimately still in-flight when the sweep's threshold elapses (very unlikely given the 20s Twilio client timeout + 5-minute default threshold) could get reaped to `failed` right before it actually succeeds — the worker logs a warning with the Twilio SID when this happens (so it's auditable), but the cart itself stays `failed` and needs manual correction. A true fix would need a full outbox pattern, judged disproportionate for a 2-day MVP on a Sandbox-only channel.
- ~~No down-migrations~~ ✅ resolved (ADR-0008, amends ADR-0006) — every migration has a paired `.down.sql`; `npm run migrate:down [steps]` rolls back the N most-recently-applied. This was an explicit reversal of ADR-0006's original trade-off, done at the user's request.
- ~~`express`/`qs` moderate advisory~~ ✅ resolved — `qs@6.16.0` patches it; added a package.json `overrides` entry to both `backend` and `mock-storefront` to reach it despite express/body-parser's semver range. `npm audit`: 0 vulnerabilities in both.
- Checkout `id`s are read as JSON numbers (`express.json()` uses `JSON.parse`), which loses precision above `Number.MAX_SAFE_INTEGER`. Fine for the mock storefront's timestamp-based ids and won't matter until a real Shopify integration (ADR-0005) — deliberately left deferred (confirmed with the user) rather than hardened proactively.
- ts-node ignores tsconfig's `include`-based ambient `.d.ts` files (like `types/express.d.ts`, used for the `req.rawBody` augmentation from ADR-0007) unless `"ts-node": { "files": true }` is set in `tsconfig.json` — already set, but worth knowing if a similar augmentation is added and mysteriously "disappears" only under `ts-node`/`npm run dev` while `tsc --noEmit` stays green.
